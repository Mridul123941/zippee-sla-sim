# When should a dark store shrink its delivery radius?

A self-initiated student case study by **Mridul Upadhyay** (B.Tech Production & Industrial Engineering, Data Science minor, Punjab Engineering College).

> **This is a simulation, not evidence.** It uses synthetic data from one imaginary dark store and clearly labelled placeholder assumptions. It does not use any company's data and does not claim real savings. The goal is to show how I frame a problem, make assumptions explicit, test them, and stay honest about what only real data can answer.

## The question

Quick-delivery promises (e.g. 60 minutes) are hardest to keep during evening surges, when orders arrive faster than a store can pick, pack and dispatch them. One lever is to temporarily **shrink the serviceable radius** so fewer, closer orders are accepted. But shrinking also means **turning orders away**.

**Can a simple breach-risk estimate tell us when shrinking is worth it, once the cost of lost orders is included?**

My hypothesis: there is a threshold where the risk avoided outweighs the orders lost, and where it sits depends heavily on assumptions I cannot verify without real data. So the project focuses on **how sensitive the answer is**.

## Project map

| File | What it does |
|---|---|
| `simulator.py` | Discrete-event simulation of one dark store (arrivals, picker queue, rider pool, travel). Pre-draws randomness per day so baseline and policy runs use the *same* orders. |
| `train_sla_model.py` | Simulates ~10k orders, trains a logistic-regression breach-risk model on 5 features, evaluates on held-out *days*, compares with two baselines. Writes `artifacts/`. |

## How it works

**Simulation.** Orders arrive as a Poisson process with a surge window (8-11 PM). Each order waits in a FIFO queue for a picker, then for a rider, then travels. Delivery time is placed-to-delivered; a **breach** is over 60 minutes. Pick-time noise and traffic noise are random and **invisible to the model**, so perfect prediction is impossible.

**Model.** Logistic regression (no class weights, to keep the scores as close to probabilities as possible) on five features known at order time: `queue_per_picker`, `items`, `distance_km`, `riders_free`, `is_peak`. Train/test split is **by day**, because orders from the same evening share a queue and a random row split would leak.

**Decision rule.** While the store-level risk (for a reference outer-ring order) is above a threshold, the geofence tightens from 5 km to 3 km and farther orders are refused. This is framed as a *suggestion for an ops person*, not an automatic action.

**Evaluation.** The same fresh days are run once with a fixed radius and once per threshold. Then:

```
net benefit = breaches avoided x (share that become RTO x RTO cost)  -  orders turned away x margin per order
```

The curve shows +/- 1 standard error across days, because a few overloaded days dominate the result.

## What I found (default settings; will change as you change assumptions)

- The fixed-radius breach rate is about 12-13% in the simulation; tightening can cut it roughly in half while refusing only a few percent of orders.
- Net benefit is **not monotonic**: tightening too eagerly (low thresholds) loses money because it refuses too many orders.
- At my placeholder costs the best threshold is broad and flat (roughly 30-50%), and the error bars are wide. I would not trust the exact optimum.
- With the default Rs 100 RTO cost and Rs 40 margin per order, tightening only pays if more than about **17%** of breached orders turn into RTOs. That share is exactly the number real data would need to supply. Below it, the right decision is to leave the radius alone.

## Honest limitations

- **Calibration is imperfect.** In the held-out check, orders scored around 26% breached only about 9% of the time, because the true pattern is closer to "safe" or "overloaded" than a smooth logistic curve. Thresholds like 30% or 50% should be read as score cut-offs, not literal probabilities. This is also why the net-benefit curve is flat across the 30-50% range: very few orders sit in that gap.

- **The model's high AUC (about 0.96-0.97) is a red flag about synthetic data, not a result.** The simulator's queue mechanics are simple and the model recovers them. A flexible gradient-boosting reference scores only slightly higher, so the logistic model isn't leaving much on the table *in this simulator*. Real operations are messier.
- The link between a late delivery and an RTO is **assumed**, not measured. It is the single most important unknown.
- Refused customers are treated as lost; in reality some would reorder later or churn.
- Left out: rider no-shows, order batching, weather, multiple stores, COD vs prepaid differences.
- Changing the store scenario in the dashboard does *not* retrain the model. That is deliberate: it shows what happens when conditions drift from what the model learned.

## What I'd want to learn from real operations

1. How is the serviceable radius changed today, and who decides?
2. Which signals exist at order time (queue length, staff on floor, rider supply)?
3. How often does a late delivery become an RTO or a cancellation, and does it differ for COD?
4. What does a refused order really cost compared with a late one?
